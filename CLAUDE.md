# CLAUDE.md

Guidance for Claude Code (and any coding agent) working in this repo.
This repo is the live demo for the Design AI 8.0 keynote "Three Gates".
A designer decides at the gates; you build. Keep every change small, real and reviewable.

## Stack

- React 19 + TypeScript (strict), Vite 7, pnpm workspace (`packages/design-system`).
- Routing: TanStack Router, file-based. Routes live in `src/routes/`; the route tree
  `src/routeTree.gen.ts` is generated by the Vite plugin (git-ignored, never edit it).
- Tables: TanStack Table, with shared building blocks in `src/components/data-table/`
  (`DataTableToolbar`, `DataTablePagination`, `DataTableColumnHeader`, ...).
- UI: shadcn/ui (new-york style, lucide icons). App components come from
  `src/components/ui/` (imported as `@/components/ui/...`). The app does not import from
  `@designai/design-system` today.
- Styling: Tailwind CSS v4 with theme tokens in `src/styles/theme.css`.
- Forms: react-hook-form + zod. State: zustand. Data fetching: TanStack Query.
- Mock data: typed files under `src/features/<feature>/data/` (faker with a fixed seed, or static arrays).

## Where things go

- A feature lives in `src/features/<feature>/` (`index.tsx`, `components/`, `data/`).
- Its route file in `src/routes/_authenticated/<feature>/index.tsx` stays thin: it wires
  `createFileRoute`, `validateSearch` (zod) and the feature component.
- Page shell: `Header` + `Main` from `@/components/layout/*`, same as `src/features/tasks/index.tsx`.
- Sidebar links: `src/components/layout/data/sidebar-data.ts`.

## Conventions

- **Use existing shadcn/ui components** from `@/components/ui` before writing new markup.
  Add a new primitive with the shadcn CLI only if nothing fits, and say so in the PR.
- **Theme tokens only.** Use `bg-background`, `text-foreground`, `text-muted-foreground`,
  `bg-muted`, `border`, `bg-primary`, `text-destructive`, `chart-1..5`, etc.
  No raw hex, rgb or oklch values in components, and no arbitrary color classes like `bg-[#ecedef]`.
  (A few legacy spots still have hex; do not copy them, and do not fix them in an unrelated PR.)
- Must work in light and dark mode, and in RTL (the app has a direction switch; prefer
  logical classes such as `ms-*`, `me-*`, `ps-*`, `text-start`).
- **TanStack Router:** read and write URL state with `getRouteApi('<route id>')`,
  `route.useSearch()` and `route.useNavigate()`. Declare every search param in the route's zod schema.
- **TanStack Table:** follow `src/features/tasks/components/tasks-table.tsx`. Use
  `useTableUrlState` (`src/hooks/use-table-url-state.ts`) so filters and pagination live in the URL.
- Imports use the `@/` alias. Prettier sorts imports; run `pnpm format` instead of ordering by hand.
- TypeScript: `type` imports (`import { type X }`), no `any`, no unused vars, no `console.*` (lint error).
- Keep copy short and in plain English. Sentence case for headings and buttons.

## Accessibility

- Every interactive element is reachable and usable by keyboard, with a visible focus ring.
- Icon-only buttons have an accessible name (`<span className='sr-only'>` or `aria-label`).
- Use semantic elements (`button`, `a`, headings in order, `nav`, `main`, lists).
- Status changes (download started, no results) are announced: use `role='status'` or `aria-live='polite'`, or a `sonner` toast.
- Do not rely on color alone; meet WCAG AA contrast with the theme tokens.

## Commands

```bash
pnpm install --frozen-lockfile --ignore-scripts   # same as CI
pnpm dev            # http://localhost:5173
pnpm lint           # eslint (CI)
pnpm format:check   # prettier (CI); pnpm format to fix
pnpm build          # tsc -b + vite build (CI)
pnpm storybook      # component docs on :6006
```

CI runs lint, `format:check` and build on every PR to `main`. There is no unit test suite;
do not claim tests you did not write or run.

## How work ships

1. One feature = one branch = one PR to `main`. Never commit to `main` directly. Never merge.
2. Branch names: `feat/<short-name>`, `fix/<short-name>`, `chore/<short-name>`.
3. Commit messages: Conventional Commits (`feat: ...`, `fix: ...`, `chore: ...`).
4. Before opening the PR, `pnpm lint`, `pnpm format:check` and `pnpm build` all pass.
5. Every PR body has:
   - **What & why**: two or three lines, and the ticket key (for example `KAN-12`).
   - **Screenshots**: before and after, light and dark if the UI changed.
   - **Test plan**: numbered manual steps a designer can follow in the preview, including
     keyboard-only and the empty or edge case, plus the commands you ran.
   - **Out of scope**: what you deliberately did not do.
6. Stay inside the ticket. If you find something else, note it in the PR instead of fixing it.
